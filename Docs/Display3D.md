# 3D立体視・ハーフミラー制御設計思想 (Display3D.md)

本ドキュメントは、Sony Spatial Reality Display (SRDisplay) 等の視線追跡（アイトラッキング）技術と、ハーフミラーを用いた光学的配置を組み合わせた「3D立体視・ハーフミラー制御モジュール」の設計思想および数理モデルについて解説します。

---

## 1. モジュール概要

本プロジェクトでは、以前実装されていた `StereoCameraController` のような独自のカメラトラッキング計算を廃止し、**「SDKのネイティブなトラッキング機能」と「描画空間の鏡像反転」を組み合わせる**、よりシンプルで堅牢なアーキテクチャへと進化しました。

これにより、物理的なアイトラッキングセンサー（`SRDManager`）が取得したユーザーの「両目の3D座標」と投影行列（フラスタム）の精度を 100% 活用しつつ、ハーフミラー越しの正しい視差（パララックス）を表現します。

**主要コンポーネント:**
*   `CameraAdjuster.cs`（ディスプレイ位置情報の提供）
*   `PCD_RenderPass_BindParams.cs`（コンピュートシェーダーでの空間鏡像化）

---

## 2. 解決すべき課題と新アーキテクチャの設計思想

ハーフミラー越しに3D空間を正しく表示・インタラクションするためには、「鏡による左右反転」と「視差（パララックス）の逆転」という重大な問題を解決する必要がありました。

### A. 投影行列（フラスタム）の反転による破綻
従来のアプローチでは、ハーフミラーの鏡像効果を相殺するために、カメラの投影行列（フラスタムの左右）自体を無理やり反転させていました。
しかし、これを行うと以下の問題が発生します。
1. **視差の逆転**: 現実の顔が右に移動した時、仮想世界の物体は左に回り込む（正しい視差）はずが、投影行列を反転させると視差の方向まで反転してしまい、気持ち悪い動きになります。
2. **カリングの反転**: 空間全体が裏返るため、ポリゴンの表裏が逆転（CCWとCWが逆転）してしまい、`GL.invertCulling = true` などの強引な補正が必要になっていました。

### B. 空間反転による「正しい鏡面世界」の構築
上記の課題を解決するため、**「カメラのトラッキングと投影行列は一切いじらず、描画される世界（空間）の方を反転させる」** というアプローチを採用しました。

### C. 数理モデルによる、X軸反転のみで成立することの説明

ハーフミラー越しの立体視において、なぜ「X軸（左右）の反転」のみで物理的な鏡像とソフトウェアの期待値のズレが解消されるのか、線形代数を用いて説明します。

#### 1. 座標系の定義
基本となる原点に対し、実際のハードウェア配置（鏡やディスプレイの位置）による空間的なズレを変数であるオフセットベクトル $T = (x_{off}, y_{off}, z_{off})^T$ などとして定義します。
* **X軸（左右）：** ユーザーから見て「右」が正 ($+X$)
* **Y軸（奥行き・目線）：** 鏡からユーザーに向かう方向が正 ($+Y$)
* **Z軸（上下）：** 鏡の面上で「上」が正 ($+Z$)

#### 2. 鏡による反射（Y軸の反転とオフセット）
ハーフミラー環境での鏡面反射は、奥行きであるY成分の反転に、鏡の位置によるY方向のオフセットが加わる変換になります。
現実の目の位置 $E$ を $(x, y, z)^T$ とすると、カメラが捉える鏡の中の虚像の目 $E'$ は以下のようになります。

```math
E' = \begin{pmatrix} 1 & 0 & 0 \\ 0 & -1 & 0 \\ 0 & 0 & 1 \end{pmatrix} \begin{pmatrix} x \\ y \\ z \end{pmatrix} + \begin{pmatrix} 0 \\ y_{off\_mirror} \\ 0 \end{pmatrix} = \begin{pmatrix} x \\ -y + y_{off\_mirror} \\ z \end{pmatrix}
```

物理的な事実として、「X（左右）」と「Z（上下）」はそのまま、「Y（奥行き）」だけが反転しオフセットが付与されます。

#### 3. ソフトウェアが期待している「対面」の座標
一般的なトラッキングソフトウェアは、「人間がシステムの正面に立って（向かい合って）いる」ことを前提に計算します。
人間が向かい合うということは、数学的には**「ディスプレイの基準位置（X軸オフセット $x_{off}$ やY軸オフセット $y_{off}$ 等）を中心に、元の姿勢を垂直な軸（Z軸）で 180^\circ 回転させた状態」**を意味します。
この期待される対面状態の座標 $E_{expected}$ は以下のようになります。

```math
E_{expected} = \begin{pmatrix} -1 & 0 & 0 \\ 0 & -1 & 0 \\ 0 & 0 & 1 \end{pmatrix} \begin{pmatrix} x - x_{off} \\ y - y_{off} \\ z \end{pmatrix} + \begin{pmatrix} x_{off} \\ y_{off} \\ 0 \end{pmatrix} = \begin{pmatrix} -x + 2x_{off} \\ -y + 2y_{off} \\ z \end{pmatrix}
```

#### 4. 矛盾の解消 ＝ 「オフセットを加味したX軸の反転」
カメラが実際に取得した虚像 $E'$ と、ソフトウェアが期待している座標 $E_{expected}$ を比較します。

* **カメラが取得した虚像：** $E' = (x, -y + y_{off\_mirror}, z)^T$
* **ソフトが期待する座標：** $E_{expected} = (-x + 2x_{off}, -y + 2y_{off}, z)^T$

ここで、ハードウェアが正しく配置・キャリブレーションされていれば、Y軸の反射によるオフセットとソフトウェア基準位置のY座標は一致（$y_{off\_mirror} \approx 2y_{off}$）します。
これを見比べると、Y（奥行き）とZ（上下）は実質的に完全に一致しており、**唯一根本的にズレているのが「Xの符号（およびその基準となるXオフセット）」**であることが分かります。

したがって、仮想ディスプレイの中心位置 $x_{off}$（実装における `center`）を基準として**「X座標だけを -1 倍（左右反転）する」**ことで、鏡の反射（Y反転）とシステムが前提とする対面回転（X, Y反転）のギャップが数学的かつ完全に埋まることが証明されます。

### D. なぜ反転の原点を「ディスプレイ」にする必要があるのか（SDK連携のメリット）

空間をX軸反転させる際、ワールド空間の原点 $(0,0,0)$ ではなく、あえて**「ディスプレイ（＝トラッキングの基準位置）」を反転の中心（ローカル原点）として鏡像空間を作る**ことには、SRDisplay SDK等の仕様上、極めて重要なメリット（うれしさ）があります。

1. **SDKの非対称フラスタム（投影行列）を無改造で利用できる**
   SRD SDKは、ディスプレイ面を基準にして「ユーザーの目がどこにあるか」を計算し、ディスプレイ枠に合わせた非常に特殊な非対称フラスタム（投影行列）を内部で自動生成しています。もし空間をワールド原点で単純に反転してしまうと、オブジェクトがディスプレイの描画領域（視錐台）から遠く離れた場所に飛んでいってしまいます。ディスプレイ位置を反転の原点とすることで、**SDKが厳密に管理している描画ボリュームの中に、反転したオブジェクト群をピタリと収める**ことができ、SDKの強力な立体視レンダリング機能を一切改造せずに「丸投げ」できます。

2. **トラッキングの相対距離（パララックス）が完全に保存される**
   前項の数式で示したように、ソフトウェア（SDK）はディスプレイ位置（$x_{off}$ や $y_{off}$）を基準に計算を行います。反転の軸をこのディスプレイ位置に一致させることで、数式上のオフセットのズレが相殺され、「カメラから見たユーザーの目の移動量」と「空間内の仮想オブジェクトの視差の移動量」の相対関係が100%維持されます。これにより、ハーフミラー越しであっても、SDKが提供する「実物がそこにあるかのようなミリ単位のトラッキング精度」を一切損なうことなく鏡像世界に持ち込むことができます。

## 3. 実装されたアルゴリズム（空間鏡像化ロジック）

カメラの投影行列はSDKの計算結果をそのまま利用し、描画されるオブジェクト群をハーフミラー面（ディスプレイ面）を基準にして左右反転させます。

### Step 1: 点群（Point Cloud）の X軸反転
点群のレンダリングを担うコンピュートシェーダーに渡す `ViewMatrix`（ビュー行列）に対して、`CameraAdjuster` から提供される `displayTransform`（ディスプレイ面）を中心とした空間反転行列を適用します。

```csharp
// 1. 点群をディスプレイ中心からの相対座標（ローカル空間）に移動
// 2. そのローカル空間内で X軸だけを -1 倍（反転）
// 3. 反転した状態のまま、ワールド空間の座標系に配置し直す（位置のオフセットを戻すだけで、反転は維持する）
Matrix4x4 displayTRS = Matrix4x4.TRS(center, rotation, Vector3.one);
Matrix4x4 flipX = Matrix4x4.Scale(new Vector3(-1, 1, 1));
Matrix4x4 displayInverse = displayTRS.inverse;

// カメラの元の ViewMatrix に反転行列を合成
vMatrix = vMatrix * displayTRS * flipX * displayInverse;
```
これにより、点群データ自体がディスプレイ面を軸にして反転配置されるため、カメラが正常に移動したときの視差（パララックス）が、ハーフミラー越しにおいて完全に正しい方向として描画されます。

### Step 2: 仮想オブジェクトの X軸反転
狐などの通常の Unity 仮想オブジェクト（メッシュ）は、点群の反転世界と一致させる必要があります。
これらは、親の `Transform` の `Scale.x` を `-1` に設定するだけで、Unityの標準機能によりカリングの破綻なく正しく反転・描画され、点群空間と完全に同期します。

## 5. 結び
この「SDKトラッキングの完全活用」と「描画空間側の鏡像反転」の導入により、トラッキングのズレやパララックスの逆転といった不具合が完全に解消されました。また、独自の複雑な座標計算スクリプト（`StereoCameraController`）を排除できたことで、パフォーマンスの向上とシステムの堅牢性が飛躍的に高まりました。

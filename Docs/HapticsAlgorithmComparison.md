# Haptics Algorithm Comparison: Native vs C#

本ドキュメントでは、元の `com.shinolab.midair-haptics-unity-core` パッケージに実装されていたハプティクス（超音波提示）生成アルゴリズムと、本プロジェクト向けに完全 C# で再設計された `HAP_AUTDController` および `HAP_HapticsSources` のアルゴリズムの違い、およびその設計思想について解説します。

---

## 1. 全体的なアーキテクチャの変更点と設計思想

### 元パッケージ (Native C++)
* **動作**: `HapticsCentroidSource` や `HapticsEllipseSource` などのロジックがネイティブ C++ 側に隠蔽されており、Unity側からは設定を流し込むだけのブラックボックスでした。また、STM（Spatio-Temporal Modulation）の生成やサンプリング処理が、複数のC++スレッド上で複雑に並行動作していました。
* **課題**: Unity エディター上で「どのようなSTM波形が出力されているか」をデバッグ・可視化することが困難でした。また、ネイティブプラグインのクラッシュが Unity 全体を巻き込んで落ちるリスクがありました。

### 本システム (Pure C# / AUTD3Sharp)
* **動作**: すべての触覚形状生成アルゴリズム（EllipseのPCA計算、Randomのサンプリング、STMフレームの合成）を、公式の C# ラッパーである `AUTD3Sharp` 上に構築された Pure C# スクリプトに移植・公開しました。
* **設計思想**: **「Unityエンジニアが触覚デザインを直接カスタマイズ・デバッグできること」** と **「Unityのメインスレッドの安定動作」** を最優先としました。複雑なネイティブスレッドを廃止し、Unityのライフサイクル (`Update`) に完全に同期する軽量な設計へと変更しています。

---

## 2. アルゴリズムの比較詳細（追加・変更・割愛した点）

### 🔴 割愛・削除した点 (Omitted)

1. **CPUでの重いランダムポイント生成**
   * **元仕様**: `HapticsRandomSource` では、毎フレーム `InsideMesh` の点群バッファをCPUメモリに展開し、そこから `std::rand()` 等を用いて乱数で数十個の座標をサンプリングしてSTMを生成していました。
   * **理由**: 毎フレームの配列操作とシャッフルはメインスレッドに大きなスパイク（プチフリ）を発生させます。そのためこのロジックをCPUから完全に削除し、GPUコンピュートシェーダー（`Reservoir Sampling`）に責務を移行しました。

2. **ブラックボックス化されたネイティブマルチスレッド (HoloNativeBackend)**
   * **元仕様**: 複数の Haptics Source がバックグラウンドスレッドで非同期にホログラフィを計算（`PcaNative`）していました。
   * **理由**: Unityのシーン上のオブジェクトの座標（Transform）へのアクセスと非同期スレッドは相性が悪く、不具合の温床でした。全てのデータ処理を GPU 側で完了させ、結果のみを C# で同期的に処理する設計に変更したため、複雑なスレッド管理が不要になりました。

3. **GainStm および Virtual Aperture 機能**
   * **元仕様**: デバイスの振動子ごとの振幅・位相を直接制御する `GainStm` モードや、振動子の指向性を詳細にシミュレーションする `HoloVirtualAperture` などの高度な音響計算が含まれていました。
   * **理由**: 計算負荷が非常に高く、一般的な用途（接触部位への焦点提示）においてはオーバースペックであったため、本プロジェクトでは削除し、軽量な `Sequential` と `FociStm` に絞り込みました。

### 🟡 C#へ移植・再構築した点 (Ported & Modified)

元のネイティブパッケージが持っていた優れた機能群を、純粋な C# (Unity 上) で動作するようにアルゴリズムを再構築しました。

1. **Ellipse Source の形状計算 (PCA)**
   * **元仕様**: ネイティブ側で厳密な特異値分解（SVD）などを用いて接触領域の主軸と副軸を計算していました。
   * **変更後**: C# 側で、GPUから受け取った「共分散行列（Covariance Matrix）」をもとに固有値問題を解き、楕円の長軸・短軸ベクトルを算出する独自実装に変更しました。

2. **Sequential モードと FociStm モードのC#実装 (HapticsOutputMode)**
   * **内容**: 従来のパッケージに存在した `Sequential`（フレームごとに1点出力）と `FociStm`（バッファ一括送信）の2つの出力モードを、AUTD3Sharp 上で動作する C# ロジックとして完全に書き直しました。
   * 特に複数接触時には、すべてのクラスタを `Sequential` で処理することで、Unityのメインスレッドをブロックすることなく $O(1)$ の極小計算量でハプティクスを提示できるように最適化されています。

3. **速度ベースのダイナミックスケーリング (Velocity Scaling)**
   * **内容**: 対象オブジェクト（手など）が速く動いている時に触覚を強く/弱くする `useFrequencyScaleBySpeed` 等のパラメータも C# 側に移植しました。前フレームの重心との差分から速度（m/s）を計算し、動的に STM の周期や音圧振幅を増減させるロジックを再実装しています。

4. **Modulation（変調）の競合解決 (Frame Policy Override)**
   * **元仕様**: `framePolicyOverride.priority` などを用いて各ソースの Modulation を解決していました。
   * **変更後**: `ModulationOverride` クラスとして C# 側に整理し、`ResolveModulationOverrides()` メソッドで最も優先度の高い設定を毎フレーム自動的に採用・適用する仕組みを構築しました。

### 🟢 追加した点 (Added)

1. **完全な Gizmo 可視化**
   * **内容**: 生成される触覚のフォーカスポイントや、楕円の軌跡、ランダムサンプルの16点の位置などを、Unityエディターの Scene ビュー上に描画するデバッグ可視化機能を追加しました。これにより、意図した触覚が意図した座標に生成されているかを視覚的に確認できるようになりました。

---

## 3. 総括

元のネイティブパッケージはブラックボックスであり、「設定を投げ込むと何かが出てくる」状態でしたが、計算の最適化やUnityらしい調整が困難でした。

本システムでは、複雑な点群処理やサンプリングを **GPU 側（Collision.md 参照）に完全にオフロード** することで CPU の余力を確保しました。そして空いた CPU（C#）側には、`Sequential` 出力モードや速度ベースの変調、優先度解決といった **「より表現力豊かで、よりゲームエンジンに適したリアルタイム触覚デザインロジック」** を追加実装しています。これにより、軽量かつ高い保守性・拡張性を持ったハプティクスシステムが完成しました。
